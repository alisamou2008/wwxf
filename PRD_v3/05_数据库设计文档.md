## 一、数据库概述

### 1.1 设计原则

1. **规范化设计**：遵循第三范式（3NF），减少数据冗余
2. **软删除**：所有业务表使用`deleted_at`字段实现软删除，不物理删除数据
3. **审计字段**：所有表包含`created_at`、`updated_at`、`created_by`、`updated_by`字段
4. **UUID主键**：所有表使用UUID作为主键，保证分布式环境下的唯一性
5. **索引优化**：为常用查询字段建立索引，提升查询性能
6. **视图聚合**：使用视图实现复杂聚合查询，简化应用层逻辑
7. **函数封装**：使用PostgreSQL函数实现业务逻辑（如BI同步、智能分案）

### 2.4 mediator_courts（人员-法院-调解组织绑定关系表，含审核）

> 本表是操作层数据可见性的总开关：调解员（含/不含主管标识）必须在此表存在 `bind_status='approved'` 的记录，才能看到对应法院的数据。**支持一个人员绑定多个法院、多个调解组织**，每条关系独立申请、独立审核。一次绑定 = 1 个法院 + 该法院下 1 个调解组织 + 关系类型。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|-------|------|------|-------|------|
| id | UUID | PK | gen_random_uuid() | 绑定ID |
| mediator_id | UUID | FK | NOT NULL | 人员ID（调解员，含/不含主管标识） |
| court_id | UUID | FK | NOT NULL | 绑定法院ID（来自 courts 主数据） |
| organization_id | UUID | FK | NOT NULL | 该绑定对应的调解组织ID（来自 mediation_organizations 主数据） |
| relation_type | VARCHAR(50) | NOT NULL | 'participate' | 关系类型：supervise（主管管辖）/ participate（参与调解） |
| is_primary | BOOLEAN | - | false | 是否主驻法院（每人仅 1 个为 true） |
| bind_status | VARCHAR(50) | NOT NULL | 'pending' | 绑定审核状态：pending（待审核）/ approved（已通过）/ rejected（已驳回）/ unbound（已解绑） |
| apply_source | VARCHAR(50) | NOT NULL | 'self' | 来源：self（人员自助申请）/ admin（管理员直接指派） |
| apply_reason | TEXT | - | - | 申请说明/绑定理由 |
| apply_material_urls | JSONB | - | '[]' | 证明材料附件URL列表 |
| applied_at | TIMESTAMPTZ | - | now() | 提交申请时间 |
| reviewed_by | UUID | FK(mediators) | - | 审核人（系统管理员）ID |
| reviewed_at | TIMESTAMPTZ | - | - | 审核时间 |
| reject_reason | TEXT | - | - | 驳回原因（驳回时必填） |
| unbound_at | TIMESTAMPTZ | - | - | 解绑时间 |
| created_at | TIMESTAMPTZ | NOT NULL | now() | 创建时间 |
| created_by | UUID | - | - | 创建人ID |
| updated_at | TIMESTAMPTZ | NOT NULL | now() | 更新时间 |

**约束**：
- 同一"人员+法院+调解组织"只允许存在一条有效绑定（bind_status ∈ pending/approved），用部分唯一索引保证；**不同法院/组织可同时存在多条绑定（一人兼管多个项目）**：
  `CREATE UNIQUE INDEX uq_active_binding ON mediator_courts(mediator_id, court_id, organization_id) WHERE bind_status IN ('pending','approved');`
- 每人仅允许一条 `is_primary=true AND bind_status='approved'`（部分唯一索引，应用层在设主驻时先清旧）。
- `rejected`（驳回）后允许重新申请生成新记录；`unbound`（解绑）后该法院数据对该账号**彻底不可见**（可见性查询只认 approved，故历史案件也一并不可见），重新绑定审核通过后恢复；两类终态均保留完整审核/操作轨迹。

**索引**：
- `idx_mc_mediator`：mediator_id
- `idx_mc_court`：court_id
- `idx_mc_org`：organization_id
- `idx_mc_status`：bind_status（审核队列、数据可见性过滤高频使用）
- `idx_mc_relation`：relation_type
- **数据可见性核心过滤**：所有操作层查询按 `mediator_id=当前用户 AND bind_status='approved'` 取其可见 court_id 集合

> 说明：mediators.organization_id 保留为"默认/主调解组织"冗余字段；多组织绑定以本表 organization_id 为准。

1. `cases.status` → `pending_assignment`，`cases.mediator_id` 清空，`cases.excluded_from_auto_assignment` 置 true
2. 写入 `assignment_audit_logs`（action_type=`return_approved`，before/after 快照）

### 2.18 fee_rules（调解费收费规则表）

> **【2026-09-16 口径变更】**：主口径调整为「应收调解费 = 诉讼费（按全国统一标的额分段累计标准）× 法院比例（courts.mediation_fee_rate，40%–50%）」。标的额不再直接作为分段费率输入，而是先算出诉讼费再乘法院比例；fee_rules 原三模式（fixed/rate/ladder）保留为**兼容/特殊场景回退**（特殊协商法院使用）。诉讼费分段标准表（litigation_fee_standards，见下）待线下对接同步数值后初始化落库，并做全量公式校验。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|-------|------|-----|-------|------|
| id | UUID | PK | gen_random_uuid() | 规则ID |
| court_id | UUID | FK | - | 适用法院，空=全局默认规则（某法院有专属规则时优先用专属） |
| case_category | VARCHAR(50) | - | - | 适用案件分类（民事/商事…），空=全部 |
| rule_name | VARCHAR(100) | NOT NULL | - | 规则名称（如"万州法院民事阶梯收费"） |
| min_amount | DECIMAL(15,2) | NOT NULL | 0 | 标的额区间下限（含） |
| max_amount | DECIMAL(15,2) | - | - | 标的额区间上限（不含），空=无上限 |
| calc_type | VARCHAR(20) | NOT NULL | - | fixed（固定额）/ rate（按比例）/ ladder（累进阶梯） |
| fixed_fee | DECIMAL(15,2) | - | - | calc_type=fixed 时的固定收费 |
| rate | DECIMAL(8,4) | - | - | calc_type=rate/ladder 时的费率（如 0.005=0.5%） |
| min_fee | DECIMAL(15,2) | - | - | 本区间保底收费 |
| max_fee | DECIMAL(15,2) | - | - | 本区间封顶收费 |
| priority | INTEGER | - | 100 | 匹配优先级（数值小者优先） |
| status | VARCHAR(20) | NOT NULL | 'active' | active 启用 / inactive 停用 |
| effective_from | DATE | - | - | 生效日期 |
| remark | VARCHAR(255) | - | - | 备注 |
| created_by | UUID | - | - | 创建人（系统管理员） |
| created_at | TIMESTAMPTZ | NOT NULL | now() | 创建时间 |
| updated_at | TIMESTAMPTZ | NOT NULL | now() | 更新时间 |

**应收计算口径**：按案件 court_id（→回退全局）+ case_category 取启用规则，定位标的额所在区间：
- fixed：应收 = fixed_fee；
- rate：应收 = 标的额 × rate，并夹在 [min_fee, max_fee]；
- ladder：按各区间分段累进求和（每段 = 落在该段的标的额 × 该段 rate），再套用保底/封顶。
- 计算结果写入 cases.receivable_fee 作为应收快照；规则变更不追溯历史案件，管理员可对单案"按最新规则重算"。

**索引**：`idx_feerules_scope`(court_id, case_category, status)、`idx_feerules_range`(min_amount, max_amount)。

### 4.1 sync_bi_daily_stats()（BI日统计同步函数）

**用途**：每日同步案件数据到bi_daily_stats表，生成平台、法院、调解员三个维度的日统计数据

**参数**：无
**返回**：VOID
**执行时机**：每日03:00通过Vercel Cron调用，或手动触发

1. 统计平台维度数据（dimension_type='platform'）
2. 按法院分组统计法院维度数据（dimension_type='court'）
3. 按调解员分组统计调解员维度数据（dimension_type='mediator'）
4. 使用UPSERT方式写入bi_daily_stats表
5. 记录同步日志到bi_sync_logs表

### 4.2 update_updated_at()（更新时间自动更新触发器）

**用途**：所有表的updated_at字段自动更新为当前时间

**参数**：无
**返回**：TRIGGER
**触发时机**：UPDATE操作前

**逻辑**：
```sql
NEW.updated_at = now();
RETURN NEW;
```

### 4.3 generate_case_number()（案号自动生成函数）

**用途**：新增案件时自动生成案号

**参数**：court_id（法院ID）
**返回**：VARCHAR（生成的案号）

**逻辑**：
1. 获取法院简称
2. 获取当前年份
3. 查询该法院当年案件数量
4. 生成案号格式：{法院简称}{年份}{6位序号}
5. 例如：FL2026000001

### 4.4 calculate_mediator_income()（调解员收益计算函数）

**用途**：汇总调解员在指定时间范围内的调解费与提成（三费口径）

**参数**：
- mediator_id（调解员ID）
- start_date（开始日期）
- end_date（结束日期）

**返回**：JSON（case_count、subject_amount_total、receivable_total、received_total、refund_total、commission_total）

**逻辑**：
1. 按费用流水 pay_time 落在区间、mediator_id 匹配，分别汇总 received/refund；
2. 应收取该区间案件 receivable_fee 合计；
3. **提成 commission_total = received_total − refund_total**；
4. 返回明细，并可按 court_id 分组（一人多法院时分别出数）。
> 旧"基础收益 + 标的提成 × 收益系数"口径保留在 mediators.income_coefficient 字段作为扩展，是否在提成基础上再乘系数，待业务确认后并入。

### 4.5 intelligent_assignment()（智能分案函数）

**用途**：根据三维度权重进行智能分案

**参数**：
- court_id（法院ID）
- case_ids（待分案案件ID数组）
- weight_count（数量权重，默认0.5）
- weight_amount（标的权重，默认0.3）
- weight_type（类型权重，默认0.2）

**返回**：JSON（分案结果，包含每个案件分配的调解员ID和匹配度评分）

**逻辑**：
1. 获取该法院所有可用调解员
2. 计算每个调解员当前的案件数量、总标的额、案件类型分布
3. 对每个待分案案件，计算分配给每个调解员的匹配度评分
4. 匹配度 = 数量均衡度×权重 + 标的均衡度×权重 + 类型匹配度×权重
5. 选择匹配度最高的调解员
6. 更新调解员的统计数据（用于后续案件的均衡计算）
7. 返回分案结果

### 4.6 calculate_receivable_fee()（应收调解费试算函数）

**用途**：根据标的额、法院、案件分类，按 fee_rules 计算应收调解费（分案/导入案件时自动算，也供前端录入实收前试算）。

**参数**：court_id、case_category、subject_amount

**返回**：应收金额 + 命中规则ID与计算过程（便于前端展示"应收如何得出"）。

**逻辑**：优先匹配该法院专属启用规则，缺省回退全局规则；按 calc_type（fixed/rate/ladder）计算并套用保底/封顶；无匹配规则时返回 0 并标记"未配置收费规则"，提示系统管理员补配。

### 4.7 generate_monthly_fee_report()（月度调解费报表生成函数）

**用途**：**次月 1 号定时生成上一个自然月**各调解员（按法院/组织拆分）的费用报表快照，写入 mediator_monthly_fee。

**参数**：p_month（目标月份 YYYY-MM，缺省=上月）、p_mediator_id（可选，单人重跑）

**逻辑**：
1. 汇总该月 case_fee_records（按 pay_time 归属月份）得到实收/退费，关联 cases 得到应收、标的；
2. commission = received − refund；
3. 按 mediator_id × court_id × organization_id upsert 到 mediator_monthly_fee；
4. 返回生成行数与批次号。管理端可手动重跑（覆盖同 UNIQUE 键旧快照）。

**调度**：与 BI 每日同步错开，建议每月 1 日 03:30 由定时任务（Supabase pg_cron / Vercel Cron）调用。

## 五、索引设计总结

### 5.1 索引原则

1. **主键索引**：所有表的id字段自动建立主键索引
2. **外键索引**：所有外键字段建立索引，提升关联查询性能
3. **常用查询字段索引**：status、created_at、court_id、mediator_id等常用筛选字段建立索引
4. **唯一约束索引**：需要唯一性约束的字段建立唯一索引
5. **复合索引**：多字段联合查询场景建立复合索引
