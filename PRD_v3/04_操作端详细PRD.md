## 一、需求背景与价值

### 1.1 模块定位

操作端是调解员（含/不含主管标识）的工作平台，核心定位是**管辖法院数据查阅 + 具体案件调解操作**。所有调解员共用同一套操作端界面，但按主管标识与机构绑定动态显示不同的菜单和数据范围。

### 1.2 带主管标识与普通调解员的页面设计区别（核心）

两者**共用同一套操作端框架和组件**，仅在"数据视角、菜单可见性、首页内容"三个层面按主管标识区分。最核心的差异是：**带主管标识者多一个「法院数据全景」全方位数据可视窗口**，用于掌握所管辖法院的整体运行状况（案件数据 + 调解员核心数据）；普通调解员没有任何团队/法院级数据窗口，只看与自己相关的数据。

#### 1.2.1 本质视角区别

| 对比维度 | 调解员·主管标识（管辖视角） | 调解员（个人执行视角） |
|---------|----------------------|---------------------|
| **核心定位** | 管辖法院数据查阅 + 本人调解操作 | 个人案件调解操作 |
| **关注对象** | "我管辖的法院 + 法院里的全体调解员 + 我自己的案件" | "我自己的案件" |
| **登录默认页** | 调解工作台（管辖法院视角，可切换法院） | 调解工作台（个人视角） |
| **数据范围** | 管辖法院所有案件（查阅）+ 个人案件（操作） | 仅个人案件 |
| **★专属数据窗口** | 有「法院数据全景」：法院案件数据 + 调解员核心数据的全方位可视化 | **无**，仅个人效能 |
| **特有菜单** | 法院数据全景（含全部案件/调解员核心数据/调解费查阅等子视图）、入驻法院项目 | 无 |
| **共有菜单** | 调解工作台、我的案件、调解进度看板、调解排期日历、待办事项、外呼记录、文书管理、AI智能体、个人效能、法规知识库；另专属「审批结案」权限 | 同左 |
| **当事人隐私** | 可查看管辖法院所有案件的当事人隐私 | 仅可查看个人案件的当事人信息 |
| **调解费/提成** | 可查看管辖范围应收/实收/退费/提成明细（含逐案下钻）；对**本人负责案件**可录入实收、退费 | 仅查看本人费用；对本人案件可录入实收、退费（提成=实收−退费） |

#### 1.2.2 侧边栏菜单可见性对比

| 侧边栏菜单 | 主管标识 | 普通调解员 | 说明 |

| 我的案件 | ✅ | ✅ | 本人参与的案件 |
| **调解进度看板** | ✅ | ✅ | 操作端专属（管理员不做）：拖拽推进阶段，审批节点留痕 |
| **调解排期日历** | ✅ | ✅ | 操作端专属（管理员不做）：排期/改期/冲突检测 |
| 待办事项 | ✅ | ✅ | 本人待办；主管另含待我审批的结案申请 |

| 入驻法院项目 | ✅ | ❌ | 主管新建/管理入驻项目 |
| 调解员管理（查阅） | ✅（并入法院数据全景子视图） | ❌ | 主管查阅管辖调解员（含收益） |
| 调解费报表（查阅） | ✅（并入法院数据全景子视图） | ❌ | 主管查阅管辖法院应收/实收/退费/提成；实收/退费录入在案件详情"费用"标签 |
| **审批结案（权限）** | ✅ **专属** | ❌ | 结案/司法确认/终结等关键节点审批，写入审计日志 |

#### 1.2.3 同一页面的内容差异（以调解工作台为例）

- **带主管标识的调解工作台**：顶部有**法院切换按钮组**（全部/涪陵/万州…），概览卡片显示**管辖法院汇总**数据，含"调解员效能排行 Top5"，并提供「法院数据全景」入口深入查看。
- **普通调解员的调解工作台**：**无法院切换**，概览卡片只显示**本人**数据，无调解员排行，无法院数据全景入口。

### 1.4 业务价值

- 对调解员：一站式完成受理、外呼、排期、文书、结案报批全流程，临期高亮支撑优先级判断；
- 对带主管标识者：法院数据全景 + 审批结案 + 收益查阅三项专属能力支撑"管团队+亲自办案"双重职责；
- 对法院院方：经全景页导出的报表用于汇报，数据不少于现有飞书万州首页。

## 二、需求目标

1. 交付操作端 17 个页面（详见第6.1节功能模块清单），其中 4 个后续阶段占位。
2. 主管标识与普通调解员共用一套界面，按标识动态显示专属模块，差异仅三项（法院数据全景、审批结案、全组收益明细查阅）。
3. 机构绑定作为数据可见性总开关：绑定法院+调解组织并审核通过才可见数据，支持多法院多组织。
4. 法院数据全景完整覆盖并超过现有飞书万州首页全部 17 个组件。
5. 案件全流程线上化：受理→调解（记录/外呼/排期）→文书（生成/签署）→结案报批（审批+留痕）→费用录入。

**四大功能域归属映射**（对齐《00》）：智能分案域→无操作端模块（仅管理员）；调解执行域→我的案件/全部案件/待办/外呼/文书/入驻项目/机构绑定；费用管理域→调解员管理/调解费报表+案件详情"费用"标签；调解知识库域→AI智能体/法规知识库/AI报表；其余为跨域支撑。

## 三、适用角色

| 角色 | 定位 | 专属能力 |
|-----|------|---------|
| 调解员·主管标识 | 管辖法院数据查阅 + 本人调解操作 | 法院数据全景（含全部案件/调解员核心数据/调解费查阅子视图）、审批结案、全组收益明细查阅、入驻法院项目 |
| 调解员 | 个人案件调解操作 | 无专属；与主管共用全部操作功能（我的案件/看板/排期/外呼/文书/效能） |

### 4.3 行数据权限

| 角色 | 数据范围 |
|-----|---------|
| 调解员·主管标识 | 查阅=已绑定且审核通过法院的全量案件（含当事人隐私、调解员收益明细）；操作=个人参与案件 |

## 五、业务流程

### 5.1 案件受理流程

新案件分派 → 待办事项出现"待受理" → 调解员确认受理（案件状态变"调解中"）或申请返回（必填理由，管理员审核）→ 进入调解执行。

### 5.2 申请返回流程（2026-09-15 统一口径，取代原"申请退回/申请重新指派"两条路径）

1. 在案件详情页点击"申请返回"按钮（审核中置灰并显示审核状态）；
2. 填写申请理由（必填）；
3. 提交申请；
4. 系统管理员在驾驶舱待处理事项/案件详情审核（同意/驳回）；
5. 审核同意后案件退回待指派池（状态→待分案、清空承办调解员、标记退出自动分案），不再纳入智能分案规则体系，由系统管理员人工指派新调解员（原调解员留痕）；
6. 审核驳回后案件仍由原调解员处理，驳回原因通知申请人。

注意：调解员不能直接退回案件，只能申请返回；同一案件可多次申请（每次留痕），审核中不可重复发起；申请记录保留在案件审计日志中。

**退案去向（2026-09-17 补充）**：申请返回审核同意后，案件进入管理端**退案管理**模块的退案池（清空原调解员、不回流公共分案池、不参与智能分案），由系统管理员在该模块人工指派新调解员（直接换人）；重新指派仅系统管理员可操作，当前不下放至调解主管（见《03》6.14、《00》15.3）。

### 5.3 结案审批流程（关键节点）

调解员/主管在案件详情提交「结案报批」「司法确认报批」「终结报批」→ 调解主管（专属）或系统管理员审批 → 通过则状态流转生效并写入审计日志；驳回则退回原阶段并通知提交人。看板拖拽遇关键节点同样触发此审批。

### 5.4 文书生成流程

选择关联案件 → 选择文书类型（调解协议书/调解笔录/收费告知书/延期申请书/其他）→ 选择模板（系统默认/个人自定义）→ 系统自动填充案件与当事人信息 → 在线编辑 → 预览 → 确认生成（状态"未签署"）→ 签署（电子签章或上传扫描件）→ 签署记录入审计日志。

### 5.5 费用录入流程

承办人在案件详情"费用"标签：登记实收（金额默认带出应收、可改、方式/时间/折扣率/凭证）→ 登记退费（金额/方式/时间/退费原因必填/凭证）→ 实时累加并重算提成（=实收−退费）→ 误走冲销（软删除留痕）→ 次月1号月度报表定格。

### 5.6 绑定申请流程

首次登录无有效绑定 → 强制引导页（不可跳过）→ 新增绑定（选法院+组织+角色+主驻标记）→ 待审核 → 管理员审核通过 → 数据可见；驳回可修改重提；解绑后该法院数据彻底不可见，重新绑定审核通过后恢复。

### 5.7 入驻法院项目流程

主管新建项目（15项字段，详见《01》）→ 上传附件（可选）→ 提交审核 → 管理员通知+审核 → 通过则法院正式入驻；拒绝可修改重新提交（仅待审核状态可编辑/删除）。

### 5.8 调解员完整工作流（案件生命周期 8 阶段，2026-09-20 同步）

> 来源：《调解员工作流-完整版》，对齐人民调解法第17-33条、《人民法院在线调解规则》及平台现有数据模型。本节为业务流程的完整基线，5.1-5.7 为其中局部路径在页面层面的落地。

#### 阶段 0 · 案件进入与受理审查（入口/分派）
- 案件来源：法院委派 / 当事人申请 / 平台流转（平台以**法院委派**为主，管理员智能分案下发，调解员不立案）
- 受理审查：管辖、可调解性、排除情形、材料完整性、关联/系列案件、是否涉众/有保全
- **排除情形（P0 合规红线，服务端闸门）**：人身关系禁止调（婚姻/收养/继承等）、当事人无/限制民事行为能力且无法定代理人、涉刑（虚假诉讼/诈骗）、已起诉且不适合委派、法律/行政法规规定只能由机关处理、损害国家/社会公共利益或第三人利益
- 分支：**受理** → 阶段1；**不受理** → 退回/转立案，写原因留痕（对应 5.1/5.2）

#### 阶段 1 · 案情掌握与初步研判（预审）
- 阅卷：案由、标的额、当事人、来源、证据线索、期限倒计时
- 身份与权限核验：实名认证（`SignSubject/verification`）、代理人资格审查（授权委托书；**特别授权才能代签调解协议**）、调解员利益冲突/回避审查
- 初步判断：调解可行性、风险（虚假调解/信访/涉众）、是否需专家、策略方向（背对背/面对面）、拟定预案

#### 阶段 2 · 通知与意愿确认（启动）
- 送达《受理告知书》+《权利义务告知书》（电子签 `ACCEPTANCE_NOTICE`）
- 取得**在线调解明示同意** → 落 `consentRecordId`（发起电子签的前置校验）
- 确认调解意愿（愿 / 不愿）；**不愿** → 终止调解/转立案

#### 阶段 3 · 争议识别与分类（关键分叉）
- **调解意愿与有无争议是两个独立维度**，必须分开判断（无争议也可能不愿调；有争议也可能愿调）
- 识别两个维度：① 有无争议 ② 争议维度（事实/金额/责任/履行）
- 分支：**无争议** → 4A；**有争议** → 4B

#### 阶段 4A · 无争议案件处理
- **真实性核验（P0，防虚假调解/恶意串通）**：是否规避债务/执行、是否损害债权人或第三人利益、是否存在胁迫/重大误解、是否借调解转移财产；核验不过则终止并提示风险
- 梳理权利义务，记载**无争议事实**
- 拟定调解方案：履行方式（一次性/分期/实物/行为）、期限、即时履行 or 分期
- **履行能力评估**（被申请人有无能力，防空协议）→ 当事人确认 → 阶段5

#### 阶段 4B · 有争议案件处理
- **争点整理**：归纳事实/法律/证据争点（对应案件字段「争议焦点」）
- **举证指导 + 证据交换/质证**，固定无争议事实
- **法律释明 + 裁判预判**：压降不合理预期
- **调解策略**：背对背/面对面、先易后难
- **多轮协商 + 方案比选**：起草→反馈→修改，多套备选
- 必要时**引入第三方**（专家/行业组织/联合调解）；**履行能力审查** → 形成合意 → 阶段5

#### 阶段 5 · 协议形成与签署（平台核心）
- **协议内容审查**（合法/可执行/自愿；违反法律强制规定/公序良俗、给付标的/主体/期限不明确、显失公平或非自愿的不制书）
- 制作《调解协议书》（按法院模板，`MEDIATION_AGREEMENT`，对应 5.4）
- **电子签署三阶段**（`stages`）：当事人双方签 → 调解员签 → 调解组织盖章
- 送达回证（`SERVICE_RECEIPT`）+ 存证（区块链/公证）

#### 阶段 6 · 效力固化（司法确认 / 赋强 / 履行）
- 告知并引导**司法确认**：调解协议生效后 **30 日内共同向法院申请**（《人民调解法》第33条，确认后具强制执行力），平台 `JudicialConfirmation`，到期前 7 天提醒
- 或**赋强公证**；或诉前调解成功**撤诉**；即时履行完毕 → 结案

#### 阶段 7 · 结案与归档
- 结案方式判定：成功（司法确认/撤诉/即时履行）/ 不成（终止）/ 撤回 / 转立案（对应 5.3 结案审批）
- 文书归档、卷宗整理（材料/笔录/证据/协议/送达回证/司法确认材料）、审计留痕（日志 ≥5 年）
- 数据回流法院/统计

#### 阶段 8 · 回访与履行跟踪（后置）
- 履行情况回访、当事人满意度、不履行预警 → 提示走司法确认/执行

#### 横切支撑（贯穿全程）
- **期限管理**：诉前调解 30 日规则（按法院×类型可配），临期预警（<10 橙 / <5 红），超期必须结案/转立案
- **流程留痕/审计**：每次通知/沟通/文书进操作日志
- **保密与数据安全**：当事人信息分级（L3/L4 脱敏）
- **中止/终止/移送分支**：一方失联/拒不到场/拒不配合、涉刑移送、反悔/撤回、期限届满未成

### 5.9 案件状态机（2026-09-20 新增基线）

```
待受理 → 已受理/已退回 → 研判中 → 通知中(待明示同意) → 意愿确认(愿/不愿) → 争议识别(无争议/有争议) → 调解中(协商/举证/方案) → 待签协议 → 签署中 → 待效力固化(司法确认/赋强/撤诉) → 已结案(成功/不成/撤回/转立案)
```

- **看板列** = 上述状态（对齐「调解进度看板」）；**待办/临期规则** = 阶段 2/3/5/6 的时限 + 30 日期限引擎；关键节点（结案/司法确认/终结）仍走 5.3 审批留痕。
- 关键判断点的 AI 辅助（受理审查、争议识别、真实性核验、争点归纳、协议审查、司法确认推荐、结案建议等 10 个「判断盒子」）见《06》AI 判断盒子接口；**AI 仅给建议，不自动改状态**。

**第四区：趋势分析**：新增 vs 结案趋势（近6个月，判断积压）；调解成功件数趋势折线（支持按案由/指派调解员维度切换分组）；近6个月核心指标趋势（案件量/结案量/成功率/标的额/实收调解费，支持指标勾选）。

**第六区：分法院明细表、多法院对比与超期预警**：① 分法院案件数据统计表（按法院逐行列出总件数/待受理/调解中/申请出具调解书/司法确认/调解结束/成功率，含合计行）；② 多法院对比（仅绑定≥2法院且选"全部"时显示：案件量、成功率、平均周期、实收调解费、调解员人数）；③ 超期预警（临近/已超调解期限案件：案号、调解员、滞留环节、天数，红色高亮，可直接下钻催办）。

**飞书万州首页组件覆盖对照（"不少于"核验）**：6张统计卡（周/月/累计委派案件量、周/月/累计实收调解费）→第一区；月/年/累计成功率环、失败原因环→第二区；按调解状态柱状、按纠纷类型标的额柱、案由分布柱→第三区；调解成功件数折线→第四区；分法院案件状态列表→第六区①；排行榜→第五区；图片装饰→替换为平台Logo/主题视觉；另增强标的区间、案件类型、新增结案趋势、多法院对比、负荷/均衡度/外呼、收益明细、超期预警等。

### 6.15 调解费报表（仅带主管标识的调解员，查阅 + 本人案件费用录入）

**模块定位与费用口径**：主管在本模块查看**管辖（已绑定且审核通过）法院**的调解费报表；主管本人也办案，故同时可对自己负责的案件录入实收/退费。主管对他人数据为**查阅**，无审核/调整权限（审核调整归系统管理员）。

**三种费用 + 提成口径（全平台统一）**：

| 项目 | 含义 | 来源 |
|-----|------|------|
| 标的额 | 案件合同纠纷金额 | 案件导入/录入 |
| **应收调解费** | 按收费规则基于标的额计算出的"应收取"金额 | 系统按收费规则自动计算 |
| **实收调解费** | 实际向当事人收取的金额（可能打折/优惠） | 调解员（含/不含主管标识）自行录入，逐笔留痕 |
| **退费** | 实际退回当事人的金额 | 调解员（含/不含主管标识）自行录入，逐笔留痕 |
| **调解员提成** | **= 实收调解费 − 退费** | 系统自动计算 |

**报表汇总区**：顶部汇总卡（选定范围的应收合计、实收合计、退费合计、提成合计，及环比）；趋势（近 6/12 个月应收 vs 实收 vs 提成对比；优惠折让额单独可见）；构成（按调解组织、按案件分类民事/商事、按调解员的费用分布）；筛选（月份默认当月、法院多绑切换、调解组织、调解员、案件分类）。

**调解员费用数据表（可下钻，核心）**：以调解员为行，列为调解员、所属调解组织、计费案件数、标的额合计、应收合计、实收合计、退费合计、提成（实收−退费）；支持按列排序、导出。行可展开下钻逐案明细（案号/案由/标的额/应收/实收/退费/提成/费用状态：未收/部分收/已结清/已退）；再点单个案件跳转案件详情页"费用"标签看每笔流水（收取时间、方式、凭证、折让说明、录入人）。一人多法院时按法院分别成行或提供法院小计/合计。

**月度报表生成机制**：次月 1 号自动生成上一个自然月的正式报表快照，生成后数值固定，作为对账/提成结算依据；当月数据为"实时累计"（流水实时汇总），跨月后以快照为准；若上月有补录/纠错，由系统管理员手动重跑该月快照，主管端只读；主管端默认展示"已生成的最近月份 + 当月实时"，并标注数据口径。

**本人案件费用录入**：主管在自己负责案件的详情页"费用"标签录入实收/退费（操作同调解员）；录入后实时计入本报表。列表对"未录入实收但已结案""应收与实收差异过大（折让超阈值）"的案件给出提示标记，便于主管跟进。

### 6.16 AI报表（日/周/月报，后续阶段·占位待细化）

> 模块状态：占位章节，P1，属「调解知识库」功能域；细节待业务确认后细化，本节仅锁定角色范围、数据来源与栏目骨架。与《03》AI报表占位章节共用同一模块，双端口径一致。

AI 基于平台数据自动生成调解运营**日报/周报/月报**，替代现有手工 Excel 填报：**调解主管**生成/查看管辖法院的运营日/周/月报（对标涪陵法院运营部日/周/月报格式），可导出、可下发院方；**调解员**查看个人维度的日/周/月数据摘要（收案/结案/收费/成功率）。

**数据来源**（不新增表，复用现有聚合）：案件量/成功率/状态分布（BI 日统计聚合，含收案/退案/在调、成功四分类：程序性撤诉/履行性撤诉/调解书/司法确认）；费用口径（费用流水/月度费用快照/财务汇总视图：收费/退费/实收/提成）；数据范围强约束：一律按当前用户已审核通过绑定法院集合过滤。

**报表栏目骨架（对标现有运营日/周/月报）**：数据区（收案数/退案数/在调案数；调解成功数四分类；收费/补贴/退费/实际收费；调解成功率；整体 vs 个案 vs 系列案三条线；今日/本周/本月/累计多周期口径）；分析区（结案分析：数量/占比/平均调解时长；案由及成功率；失败原因五分类：联系不到当事人/分歧较大/明确拒绝/其他/撤回）；文字区（工作进展及计划、需院方或总部支持事项、平台问题——AI 生成草稿+主管人工确认后定稿）；生成节奏（每日下班前/每周五/每月底，对齐现有填报时间点，支持手动生成与重生成、导出 Excel）。

### 6.17 我的机构绑定（法院 + 调解组织）

**机制概述**：调解主管、调解员登录工作台后，**必须先绑定"法院"和"调解组织"，且经系统管理员后台审核通过后，才能看到对应法院的案件与数据**。这是操作层所有数据可见性的总开关。

- **业务三级关系**：业务主体是**法院**，法院把本院调解案件**委派给调解组织**（**一家法院可对接多家调解组织**），组织再把案件**分配给调解员**；**调解主管同时也兼任调解员**。绑定关系正是这一链条在账号侧的映射；
- **主数据来源**：法院、调解组织名称由系统管理员在管理后台统一维护（见《03》基础数据），人员绑定时只能从下拉列表选择，不能自行新增名称；
- **绑定关系**：一次绑定 = 选择 1 个法院 + 该法院下对应的 1 个调解组织 + 本人在该关系中的角色（调解员）；
- **支持多绑**：一个人可同时提交/拥有多条绑定，跨多个法院、多个调解组织；每条绑定独立申请、独立审核、独立生效，互不影响；
- **审核生效**：只有系统管理员审核通过后该法院数据才可见；被驳回后可修改并重新申请（保留历史记录）；
- **最小可用原则**：只要存在至少 1 条"已通过"的法院绑定，即可正常使用工作台。

**首次登录/无有效绑定时的强制引导**：登录后系统检测绑定关系，若无任何"已通过"绑定，**弹出全屏引导页（不可跳过进入业务数据）**，提示"您尚未绑定法院/调解组织，或绑定正在审核中，审核通过后才能查看案件数据"，提供【去绑定】与【查看我的绑定状态】；若已有"待审核"申请，引导页显示"您的绑定申请正在审核中"，不阻塞查看申请状态，但业务列表/看板仍为空态；被驳回时引导页用警示色显示驳回原因，并提供"重新编辑提交"。

**绑定申请表单字段**：

| 字段 | 控件 | 必填 | 说明 |
|-----|------|-----|------|
| 选择法院 | 下拉搜索 | 是 | 只能选系统已录入、处于"启用"状态的法院 |
| 选择调解组织 | 级联下拉（随法院联动） | 是 | 该法院下已维护的调解组织 |
| 本人角色 | 单选 | 是 | 调解员（统一注册，不选主管；主管标识由管理员在账号审核时勾选） |
| 是否主驻法院 | 开关 | 否 | 多绑时标记 1 个主要驻点，用于默认展示 |
| 申请说明 | 文本域 | 否 | 向审核管理员说明绑定理由 |
| 证明材料 | 附件上传 | 否 | 派驻证明/合作材料等 |

提交规则：同一"法院+调解组织"不允许重复提交待审核/已通过的申请（防重）；提交后进入管理员审核队列；提交后给系统管理员发系统内通知（可叠加飞书/短信，后台可配）。

**我的绑定列表**：卡片或表格展示本人全部绑定关系，每条显示法院名称、调解组织、角色、主驻标记、审核状态、申请/审核时间、驳回原因、审核人。

| 状态 | 含义 | 可执行操作 |
|-----|------|-----------|
| 待审核 | 已提交，等待管理员审核 | 撤回申请 |
| 已通过 | 审核通过，**该法院数据可见** | 设为主驻、申请解绑 |
| 已驳回 | 管理员驳回（带原因） | 查看原因、重新编辑提交 |
| 已解绑 | 主动/被动解除绑定，**该法院案件信息彻底不可见** | 重新申请，审核通过后重新可见 |

多法院绑定时，顶部和各看板的"法院切换"按钮只列出"已通过"的法院；主驻法院默认置顶、作为登录后默认数据范围。

**绑定状态对各功能数据范围的影响（强约束）**：见第4.3节。后端所有查询统一注入"已绑定且审核通过的法院集合"作为过滤条件，前端隐藏不等于安全，必须在接口层强制过滤。

**解绑与变更**：
- **解绑即彻底不可见（明确口径）**：一旦某条法院绑定被解绑（本人主动申请或系统管理员停用），该账号对该法院的**案件信息彻底不可见**——案件列表、法院数据全景、全部案件、费用报表等所有入口都不再出现该法院任何数据（含历史案件），不是"只读保留"；后端数据查询立即剔除；重新绑定并审核通过后才会再次可见；
- **主动解绑**：二次确认（提示"解绑后该法院案件信息将彻底不可见"）后生效；可配置为"本人发起→管理员确认"或"即时生效"，默认即时生效并留痕；
- **管理员停用**：系统管理员可在管理端直接停用某条绑定（人员离职/调岗），操作留痕，停用后同样彻底不可见；
- **变更法院/组织**：不直接修改原绑定，按"新增一条绑定 + 解绑旧绑定"处理，保留完整申请/审核/解绑历史轨迹（历史轨迹仅记录操作事实，不代表数据仍可见）。

### 6.18 案件详情页（多标签页，双端共用）

案件调解工作的核心操作界面，采用多标签页结构。调解主管和调解员共用同一套案件详情页，但根据权限显示不同的操作按钮。

**标签页结构**：

```
┌─────────────────────────────────────────────────────────────┐
│  ← 返回列表    案件详情 - FL2026090001                      │
│  [法院：涪陵区人民法院] [状态：调解中] [调解员：张XX]       │
├─────────────────────────────────────────────────────────────┤
│  [基本信息] [当事人信息] [调解记录] [外呼记录] [文书管理]    │
│  [分案与审计] [费用] [案件AI分析（后续）]                    │
├─────────────────────────────────────────────────────────────┤
│  当前标签页内容                                                │
└─────────────────────────────────────────────────────────────┘
```

**标签页1：基本信息**：案件ID编号、所属法院、案由（案件类型）、标的额、审理程序（简易/普通程序）、调解流程（诉前/先行/诉中调解）、立案日期、受理日期、委派时间、调解截止时间、案件状态、调解地点、网络会议地址、案情分析、诉讼请求、纠纷及达成的协议。操作权限：调解员可编辑案情分析、诉讼请求、纠纷协议等字段；调解主管仅查阅不可编辑；系统管理员可编辑所有字段。

**标签页2：当事人信息**：原告/被告/第三人信息（姓名、手机号、地址、其他信息）、当事人数量、同意数量。隐私说明：调解员仅可查看个人案件的当事人信息；调解主管可查看管辖法院所有案件的当事人隐私信息；系统管理员可查看所有。

**标签页3：调解记录**：时间线形式——调解时间、地点、参与人员（调解员、原告、被告、第三人）、调解内容、调解结果、会议纪要、发起会议按钮（网络会议）。操作：新增/编辑调解记录、发起网络会议。

**标签页4：外呼记录**：时间线形式——外呼时间、对象、当事人姓名电话、通话时长、结果、备注、录音播放。操作：新增外呼记录（必须上传录音）、播放录音、编辑。详见第6.8节。

**标签页5：文书管理**：文书列表（名称、类型、生成时间、签署状态）、预览、下载、签署。操作：生成新文书（类型+模板+在线编辑）、预览、下载、签署、重新生成。详见第6.9节。

**标签页6：分案与审计**：分案记录（分案时间、方式（智能分案/人工指派）、分案规则、原/新调解员）、分案规则详情（三维度权重）、申请返回记录（申请人、时间、理由、审核状态、审核人、审核时间、驳回原因）、操作审计日志（所有操作按时间倒序；**系统管理员通过「全部案件」操作案件时，操作记录显式标识「系统管理员操作」**，与调解员操作区分——2026-09-15 已确认）。操作功能：审核申请返回（仅系统管理员）、对已返回案件人工指派新调解员（仅系统管理员）；结案审批操作与申请返回操作详见第5.2/5.3节。

**标签页7：案件AI分析（后续阶段·占位，第一阶段隐藏）**：AI案件分析报告、类案检索结果、调解策略建议、相关法规推荐；操作：生成/重新生成AI分析、复制、导出、查看类案/法规详情。详见第6.10节。

**案件内侧边栏 AI 助手（后续阶段·网页端AI智能体唯一形态，2026-09-17 补充）**：打开案件详情页，右侧可拉出 AI 助手面板，上下文自动绑定当前案件（会话绑定 case_id，切换案件自动切换/清空上下文，不做全局聊天框）；详见《00》第十六章。
- **交互结构**：快捷按钮区（提炼案件争议焦点 / 生成调解沟通话术 / 生成调解协议初稿 / 案件风险识别，可扩展案情摘要、案件标签识别、工作量建议）+ 自由提问输入框；点击快捷按钮即带当前案件 ID 调后端固定指令，无需手动打字；
- **回填能力**：AI 输出文本支持一键复制、一键回填到当前页面的调解记录（标签页3）、文书编辑框（标签页5），调解员在此基础上修改；
- **安全与提示**：AI 调用全部经后端中转（前端不存任何密钥）；每次请求后端校验登录身份+案件访问权限；输出区域固定醒目提示：「AI生成内容仅供办案参考，正式文书请人工核对修正」；
- **数据边界**：后端按任务类型做数据裁剪与脱敏（身份证号/手机号可配置隐藏）后再传大模型；长案情由后端摘要压缩。

**标签页8：费用（应收/实收/退费/提成）**：
- **顶部费用摘要**：标的额、应收调解费（规则自动计算，展示命中规则与计算过程，可点"按最新规则重算"）、实收合计、退费合计、提成（实收−退费）、费用状态（未收/部分收/已结清/已退费）、优惠折让额（应收−实收）；
- **费用流水时间线/表格**：逐笔列出实收、退费记录——类型、金额、收取/退回方式、发生时间、折扣率、原因/说明、凭证附件、录入人、录入时间；支持查看凭证大图；
- **录入操作**（案件负责调解员/其主管可录，主管对他人案件只读）：【登记实收】金额（默认带出应收，可改为打折/优惠后实收金额）、收取方式、收取时间、折扣率、优惠说明、凭证上传（可多张），提交后实时累加实收、重算提成；【登记退费】金额、退回方式、时间、**退费原因（必填）**、凭证，提交后累加退费、重算提成；支持分次收取、多次退费；误录走"冲销"（软删除并留痕），不允许无痕删除；录入即写费用流水并回写案件三费汇总，同时计入报表与BI；正式月度报表次月1号定格；
- **校验与提示**：实收/退费金额必须 > 0；退费累计不得超过实收累计（超出时阻断并提示）；实收显著低于应收（折让超系统设置阈值）时给出黄色提示但不阻断（业务允许优惠）。

| 绑定关系 | 增（申请，防重）、改（撤回/设主驻/重新编辑提交）、删（解绑=彻底不可见） |
| 入驻项目 | 增（新建）、改（仅待审核可编辑）、删（仅待审核可删除）、查 |
| 待办 | 查+批量受理+标记完成（不影响案件状态） |
| 收藏/搜索历史（法规库） | 增/删/查，本地存储 |

## 九、校验&异常场景

| 场景 | 校验/处理规则 |
|-----|--------------|
| 无有效绑定 | 全屏强制引导页，不可跳过进入业务数据；业务列表/看板空态；接口层强过滤 |
| 绑定驳回 | 引导页警示色显示驳回原因，提供重新编辑提交 |
| 重复绑定申请 | 同一"法院+调解组织"不允许重复提交待审核/已通过的申请 |
| 解绑 | 二次确认；解绑后该法院案件（含历史）彻底不可见 |
| 临期高亮 | 剩余天数 <5 红 / <10 橙 / ≥10 绿，阈值可配置；默认按剩余天数升序 |
| 看板审批节点 | 结案/司法确认/终结必须弹审批确认并写审计日志，未通过卡片退回原列 |
| 排期冲突 | 同一调解员同时段冲突高亮提示；场地冲突同样提示；提交前冲突检测 |
| 外呼录音 | 必须上传（强制）；格式 mp3/wav/m4a；≤50MB |
| 费用金额 | 实收/退费必须 >0；退费累计不得超过实收累计（超出阻断）；折让超阈值黄色提示不阻断 |
| 费用误录 | 冲销（软删除留痕），不允许无痕删除 |
| 月度快照 | 生成后数值固定；纠错由管理员重跑，主管端只读 |
| 申请返回 | 必填理由；审核中按钮置灰防重复；驳回后可再次发起；同意后退出自动分案 |
| 主管越权 | 主管对他人案件仅查阅，编辑按钮置灰/隐藏；无分案/系统设置/操作日志/费用审核权限 |
| 空状态 | 无绑定法院或已绑法院暂无数据时，分别显示"去绑定"引导与"该法院暂无案件数据"，不用 0 伪造趋势图 |
| 隐私口径 | 全景窗口对主管开放当事人隐私（下钻案件可见），但聚合层不展示手机号等敏感明细 |

## 十二、非功能需求

1. **30 秒判断**：我的案件列表须支撑"30 秒内定位今天必须处理的临期案件"（临期色标+固定列+默认升序）。
2. **数据刷新**：全景页加载时拉取，案件上传/分案/结案后实时推送刷新；BI 趋势数据每日凌晨同步；支持手动刷新；看板顶部显示最近更新时间。
3. **数据口径与来源**：聚合数据来自 BI 日统计（法院/调解员维度）；实时性要求高的在办量、超期列表直查案件实时表；实收调解费取自财务/费用相关表；数据范围严格限定为已绑定且审核通过的法院。
4. **权限刚性**：前端隐藏菜单不能替代后端过滤；主管差异仅三项专属能力。
5. **导出能力**：全景页可导出 Excel/图片报表用于向法院院方汇报；调解费报表、费用数据表、效能明细支持导出。
6. **后续阶段模块**：AI智能体、法规知识库、AI报表、案件AI分析标签页第一阶段不实施（菜单隐藏或置灰占位），设计保留作为后续实施依据。
7. **电子签实现方式待确认**：先实现文书生成和下载，电子签确认后补充（见第13章）。
