## 一、需求背景与价值

现有飞书多维表工作流以表格呈现，操作复杂、对调解员不友好；平台升级为网页版管理后台时，需要一份覆盖全平台页面的任务基准，明确每个页面的主任务、主信息与用户动作，作为开发评审与验收的依据。本文档承担该职责，并对齐各 PRD 的业务规则，避免"业务规则散落、页面口径不一"。

---

## 二、需求目标

1. 覆盖全平台 35 个页面（第一阶段 31 个 + 后续阶段占位 4 个）的角色归属、主任务、信息骨架与验收口径。
2. 每个页面只服务一种主任务，信息按"主信息—关联信息—用户动作"三层组织。
3. 页面骨架映射与表达方式全平台统一，降低用户学习成本。
4. 沉淀两个定制业务规则（文书模板带法院维度、期限规则引擎），作为数据模型必须支持的护城河能力。

## 三、适用角色

| 角色 | 层级 | 默认页 | 专属页面 | 主任务侧重 |
|-----| --- | ----- | -------------------------------------------------------------- | ------------------- |
| 系统管理员 | 设置层 | 调解驾驶舱 | 智能分案、法院/调解员管理、费用月结、期限规则配置、操作日志、系统设置 | 全平台监控、配置、分案、财务 |
| 调解员（主管标识） | 操作层 | 调解工作台 | **拥有调解员全部功能**（我的案件/待办/外呼/文书/个人效能/看板/排期日历）+ ★法院数据全景（普通调解员无）+ 审批结案 + 全组收益明细查阅 | 亲自办案+带团队+管辖法院全量数据查阅 |
| 调解员（普通） | 操作层 | 调解工作台 | 我的案件、待办、外呼、文书、个人效能 | 个人案件执行+外呼+文书 |

> **带主管标识的调解员本质仍是调解员**：操作端所有页面（含看板、排期日历）均可见可用；差异仅在三权限：「法院数据全景」「审批结案」「全组收益明细查阅」。
> 机构绑定（法院+调解组织）审核通过后才可见数据，支持多法院。分案与名册仅系统管理员可见。

## 五、业务流程

### 5.1 申请返回全链路（2026-09-15 新增，验收第 8 条）

调解员在案件详情点「申请返回」（必填理由）→ 管理员驾驶舱待处理出现"申请返回审核"→ 同意后案件退回待分案池且**不出现在智能分案待分列表**、清空当前调解员 → 管理员人工指派新调解员（原调解员留痕）→ 驳回后案件留原调解员名下且申请人收到驳回原因；审核中按钮置灰，驳回后可再次发起。

### 5.2 看板拖拽流转

拖拽案件到下一阶段 → 普通流转直接写流转记录 → 遇结案/司法确认/终结等审批节点 → 弹出审批确认 → 写入审计日志。

### 5.3 文书生成流程

选本法院模板生成预览 → 填充案件与当事人信息 → 电子签 → 下载归档（模板带法院维度，支持按法官习惯添加自定义模板）。

### 5.4 期限规则联动流程

管理员按法院×案件类型配置期限规则 → 规则引擎重算受影响案件剩余天数 → 我的案件列表、调解进度看板、驾驶舱/法院数据全景三处"剩余天数/临期高亮"联动更新。

### 6.2 重点页面任务卡（8 张）

**① 我的案件 / 案件管理（列表）**
- 服务对象：调解员/主管（本人承办）+ 管理员（全部）
- 主任务：30 秒内判断"哪些案子要我先处理"
- 主信息：案号、案由、标的额、**剩余天数（临期高亮）**、当前阶段、承办调解员
- 关联信息：当事人双方、调解组织、来源、三费汇总
- 用户动作：打开详情、人工指派新调解员（管理员，用于已返回案件）、标记跟进
- 骨架：高密度表格；剩余天数列固定显示、临期色标（<5红/<10橙/正常绿）；表头排序 + 阶段/承办人/法院筛选；调解员默认过滤"承办人=我 + 已绑定法院"

**② 案件详情（多标签页主从工作台）**
- 服务对象：双端（权限差异化）
- 主任务：理解"这个案子怎么回事"并产出文书/记录
- 主信息：案件主体（案由/当事人/期限倒计时/阶段）
- 关联信息：标签页——基本信息/当事人信息/调解记录/外呼记录/文书管理/分案与审计（含申请返回）/案件AI分析
- 用户动作：记笔录、生成文书、提交结案报批（触发审批）
- 骨架：主从工作台（多标签页），调解记录以时间线呈现

**③ 调解进度看板【操作端专属】**
- 服务对象：调解员/主管（管理员不做）
- 主任务：一眼看"案件卡在哪个阶段"
- 主信息：阶段分布（列=状态枚举）
- 关联信息：卡片内仅标题+承办人+剩余天数
- 用户动作：拖拽推进阶段（遇审批节点→提交审批+留痕）

**④ 调解排期日历【操作端专属】**
- 服务对象：调解员/主管（管理员不做）
- 主任务：看"调解员时间有没有冲突、场地够不够"
- 主信息：时间占用（开始/结束、调解员、场地）
- 关联信息：参与当事人、案号
- 用户动作：新建/改期/查冲突（冲突颜色提示、周/月切换）

**⑤ 文书管理（双端 · 按法院模板）**
- 服务对象：双端（生成以操作端为主，模板维护在管理端）
- 主任务：按本法院模板生成并签署文书（支持自定义模板可多个，不同法官可能有自己习惯的文书风格，则以匹配法官的风格添加自定义文书模板）
- 主信息：文书列表（类型/状态/所属法院/签署状态）
- 关联信息：案件、当事人字段、模板版本
- 用户动作：选模板生成预览、电子签、下载

**⑥ 智能分案（管理端 · 强制下发）**
- 服务对象：系统管理员
- 主任务：把法院委派案件均衡分派给调解员
- 主信息：待分案池、三维度权重、推荐结果
- 关联信息：调解员负载、组织、法院
- 用户动作：配置权重、人工审核调整、确认分派（落分案记录与审计）

**⑦ 调解驾驶舱 / 法院数据全景（监控）**
- 服务对象：管理员/主管（全景为主管专属）
- 主任务：看"哪里积压、谁超期、待我审批多少"
- 主信息：异常优先（超期/临期/待审批卡片）
- 关联信息：趋势、分法院/分调解员下钻
- 用户动作：点异常卡下钻到案件

**⑧ 调解期限规则配置【管理端】**
- 服务对象：系统管理员
- 主任务：按法院×案件类型配置调解期限与可延长规则
- 主信息：规则列表（法院/类型/期限天数/可延长/阈值）
- 关联信息：影响所有页面的剩余天数计算
- 用户动作：新增/编辑规则、生效校验

## 九、校验&异常场景

| 场景 | 校验/处理规则 |
|-----|--------------|
| 临期高亮 | 剩余天数 <5 日红、5≤天数<10 橙、≥10 绿（三处页面统一） |
| 看板审批节点 | 结案/司法确认/终结必须弹审批确认并写审计日志，不允许静默流转 |
| 排期冲突 | 同一调解员同时段冲突必须颜色提示，不允许静默保存 |
| 分案排除 | 经申请返回退回待分案池的案件不出现在智能分案待分列表 |
| 权限裁剪 | 主管/调解员端不出现分案入口；普通调解员不可见任何他人/法院汇总数据 |
| 申请返回审核中 | 按钮置灰防重复发起；驳回后可再次发起 |
| 期限规则变更 | 同法院×类型不得重复启用；变更后剩余天数联动重算 |
| 模板法院维度 | 文书生成时必须按所属法院过滤模板；无可用模板时明确提示 |

## 十二、非功能需求

1. **30 秒判断**：案件列表须支撑"30 秒内定位今天必须处理的临期案件"（临期色标+固定列+排序）。
2. **一页一主任务**：每个页面只服务一种主任务，信息分主次呈现，禁止堆砌。
3. **两个定制业务规则必须被数据模型支持**：文书模板带法院维度（版本/占位符/签章文号规则，生成时按案件与当事人填充，管理员维护、操作端调用）；期限规则引擎（期限一律后端计算，前端只读渲染，"诉前30日"仅默认值，影响三处剩余天数渲染）。
4. **权限刚性**：分案与名册仅管理员可见；主管差异仅三权限；机构绑定为数据可见性总开关。
5. **验收清单（沿真实任务走一遍）**：
   1. 打开我的案件，30 秒内定位今天必须处理的临期案件（临期色标生效）；
   2. 看板拖动案件到下一阶段；遇结案节点弹出审批，确认后写审计日志；
   3. 案件详情多标签页能看完诉求/证据/笔录，并一键按本法院模板生成调解协议预览+电子签；
   4. 排期页看出某调解员同时段冲突；
   5. 驾驶舱/全景能直接看到"超期数/待我审批数"，下钻到具体案件；
   6. 改一个法院期限规则后，列表剩余天数随之变化（验证规则引擎贯通）；
   7. 智能分案由管理员完成，主管/调解员端看不到分案入口，只能收到分派结果；
   8. 申请返回全链路按第 5.1 节通过。
