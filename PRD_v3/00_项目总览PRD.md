## 一、需求背景与价值

### 1.1 项目起源

问问小法调解平台是独立开发的案件调解服务平台，目前已与涪陵区人民法院、万州区人民法院等多家法院建立合作关系，通过飞书多维表进行案件调解工作的流程管理。随着业务规模的扩大和法院数量的增加，现有飞书多维表工作流在以下方面存在明显不足：

1. **交付体验不佳**：多维表以表格形式呈现，操作复杂，对调解员不够友好
2. **功能受限**：多维表能力有限，无法实现智能分案、AI辅助、动态BI等高级功能
3. **数据孤岛**：各法院数据分散，难以进行全平台的数据分析和监控
4. **权限管理粗糙**：无法实现精细化的角色权限控制
5. **移动端体验差**：调解员在外出调解时操作不便

### 1.2 项目定位与目标

本项目**现状基线**：现有业务（涪陵、万州等法院调解项目）基于飞书多维表运作（调解工作台 84 字段、万州首页等），本平台并非简单照搬，而是**对现有业务逻辑与交互的全面优化重建**——重组流程、重定义口径、重设计交互，在保留业务实质的基础上系统性提升交付效率与体验。为调解组织及调解员提供案件管理，材料整理、AI辅助分析、复盘；不侵入法院原有分案与业务系统，本平台只做辅助分案/智能推荐，不直接改写外部平台数据。案件信息来源于调解组织或调解员授权查看后的快照导入或手动录入，仅作为本系统内部分析使用，不具备官方效力。

将现有飞书多维表工作流全面升级为独立的网页版SAAS管理后台"问问小法调解平台"，实现：

1. **全流程重构**：将法院调解全过程的全流程、全环节进行重构，提升调解员操作便利性
2. **管理灵活性**：解决调解平台管理员对所有案件的监控和管理灵活性
3. **数据可视化**：为法院院方提供直观、实时、动态的数据可视化呈现
4. **AI赋能**：通过AI智能体和知识库，帮助调解员提升调解成功率
5. **多法院支持**：天然支持多法院、多调解组织的平台化管理

### 1.3 业务价值

- 对调解员：操作便利、期限可控、文书一键生成，替代多维表手工操作；
- 对调解组织主管：管辖法院数据全景与团队收益透明，管理有据；
- 对平台管理员：全平台监控、智能分案、费用闭环，运营可控；
- 对调解组织：对调解员的工作能力评估可视化，给法院提供严谨的案件整理与分析报告；
- 对法院院方：实时动态的数据可视化，对标分析与监督有抓手。

## 三、适用角色

### 3.1 两层架构

```
┌─────────────────────────────────────────────────┐
│              问问调解平台                         │
├──────────────────────┬──────────────────────────┤
│      设置层           │       操作层              │
│  （系统管理员）        │      （调解员）  │
│                      │                          │
│  · 全平台监控         │  · 管辖法院数据查阅       │
│  · 系统设置           │  · 具体案件调解操作       │
│  · 元数据管理         │  · 外呼/文书/AI辅助      │
│  · 智能分案           │  · 个人效能管理           │
│  · 财务审核           │                          │
└──────────────────────┴──────────────────────────┘
```

### 3.2 两级角色 + 主管标识（详见《01》）

登录身份仅两种：系统管理员（admin）/ 调解员（mediator）；「是否为主管」是调解员的管理属性，由系统管理员在注册审核时勾选。带主管标识者拥有调解员全部功能 + ★法院数据全景 + 全组收益明细查阅。

> 角色定义、权限矩阵、菜单结构等细节以《01_角色与权限设计PRD》为单一事实来源，本文档不复述（避免双处维护漂移）。

### 3.3 业务委派关系（法院 → 调解组织 → 调解员）

```
 法院（业务主体）
   │  委派本院调解案件（一家法院可对接多家调解组织）
   ▼
 调解组织
   │  把法院委派的案件分配给调解员
   ▼
 调解员（带主管标识者兼具管辖职责，既管团队也亲自办案）
```

- 案件链路：**法院**是主体，把案件委派给**调解组织**，组织再分配给**调解员**；案件同时记录所属法院、调解组织、承办调解员。
- 人员通过"机构绑定"获得"法院 + 调解组织"的可见与办理资格，支持一人多法院/多组织（详见《01》《04》）。

## 五、业务流程

### 5.1 端到端主流程

法院委派案件 → 平台受理（待分案，可编辑纠错）→ 智能分案（系统管理员：数据筛选+三维度权重+人工审核）/转案人工指派 → 调解员承办（调解执行：外呼、调解记录、排期、文书生成与签署）→ 关键节点申请及审批（转案/延期/结案/司法确认，管理员或调解员审批+留痕）→ 费用录入（实收/退费逐笔留痕）→ 月结（次月1号生成上月报表快照）→ BI 面板与 AI 报表（后续阶段）呈现。

### 5.2 机构绑定流程

人员注册（选择法院+调解组织，自动生成待审核绑定申请）→ 系统管理员审核 → 通过后可见数据（支持多法院）→ 离职/调岗可停用绑定（彻底不可见）。详见《01》《03》。

### 5.3 调解费与提成模型

```
标的额 ──按收费规则计算──► 应收调解费
                              │ 实际可打折/优惠（人员录入）
                              ▼
                          实收调解费 ──减──► 退费（人员录入）
                              │
                              ▼
                    调解员提成 = 基于实收调解费总和按档位规则核算
```

**计算公式（已确认口径）**：案件标的额 →〔全国诉讼费分段累计标准（内置于系统）〕→ 诉讼费；诉讼费 ×〔该法院预置比例（40%–50%，逐法院配置）〕→ 应收调解费；实收调解费（逐笔录入）− 退费 → 提成核算原值。诉讼费按《诉讼费用交纳办法》全国统一标的额分段标准计算，与案由/民事商事属性无关；法院比例在「系统设置→各法院规则设定→调解费规则」中逐法院配置。

- **应收**：系统按上述公式计算（旧三模式收费规则保留兼容）；
- **实收、退费**：调解主管/调解员逐笔自行录入并留痕（凭证、方式、折让/退费原因），支持分次收、多次退；退费累计不得超过实收累计；
- **提成核算**原值为**实收调解费总和**，档位细则待业务补充（见《03》6.9、《01》费用模型）；**次月 1 号生成上月费用报表快照**，调解员费用可下钻到逐案，管理端与主管端均展示。

详见《01》第七章、《05》费用三表。

### 5.4 调解执行工作流概要（8 阶段）

调解员承办案件的生命周期为 8 阶段：**受理审查 → 案情掌握与初步研判 → 通知与意愿确认（在线调解明示同意，电子签前置）→ 争议识别与分类（无争议/有争议分叉处理）→ 协议形成与签署（电子签三阶段）→ 效力固化（司法确认/赋强公证/撤诉）→ 结案与归档 → 回访与履行跟踪**。

**案件状态机**：`待分案 → 已指派（无受理确认）→ 研判中 → 通知中(待明示同意) → 意愿确认 → 争议识别(无争议/有争议) → 调解中 → 待签协议 → 签署中 → 待效力固化 → 已结案(成功/不成/撤回/转立案)`；看板列、待办/临期规则均对齐该状态机。

**横切支撑**：期限管理（诉前 30 日、临期预警 <10 橙/<5 红、超期必须结案/转立案）、流程留痕审计、数据分级脱敏、中止/终止/移送分支。

**关键节点口径**：司法确认、结案状态无需在自有系统内手动操作，通过代码从官方平台自动同步，仅同步案件结案状态、结案日期、司法确认申请状态三类核心字段；案件逾期默认时效**简易程序 7 天、普通程序 15 天**，延期仅可申请 1 次、固定延长 30 天，需双方当事人签署延期申请书后上传官方平台完成；案件到期前 2–3 天由调解员提前联系当事人确认调解意向，确认可继续调解的再走延期流程。

阶段级详设与状态机枚举以《04》5.8/5.9 为单一事实来源；91 字段落位见《05》2.24。

### 5.5 数据同步链路概要（双入口抓取）

外部案件数据经双入口抓取进入平台：**入口A**（AI 智能体，调试/补录）与**入口B**（网页按钮 → 管理员本机 FastAPI 服务，业务主入口）统一输出标准 JSON Schema，经**公共飞书写入模块**按案号 upsert 去重后写入**飞书多维表（缓冲校对层）**，再单向增量同步至 **Supabase（业务主库）**，禁止反向写回。

```
入口A（AI智能体）╮                                        ┌──────────────┐
                ├→ 公共写入模块（案号去重）→ 飞书多维表（人工校对）→ │   Supabase   │
入口B（网页按钮）╯                                        └──────────────┘
```

**数据主库口径**：**Supabase 为业务主库**，业务读写均走 Supabase；飞书多维表定位为抓取缓冲与人工校对层（原「多维表=唯一数据源」口径废止）。管理端页面、可行性评估结论与分阶段落地路线见《03》§6.16；接口见《06》§5.20；任务表与来源追溯字段见《05》2.26/2.27。

- **案件状态流转**：待分案→已指派→调解中→待签署→已结案/已结束/已退回；转案/结案/司法确认等关键节点须审批+留痕；申请转案同意后转入转案池并人工指派，不再纳入智能分案。
- **基础数据**：法院/调解组织有关联数据时禁止删除；绑定主数据是机构绑定下拉的唯一来源。
- **费用数据**：实收/退费逐笔录入留痕，纠错仅限管理员；月结快照定格、可留痕重跑。
- **规则配置**：分案/收费/期限规则按法院维度维护，变更不追溯历史案件（应收可单案重算）。

## 九、校验&异常场景

**本章为总览级汇总**，完整校验与异常场景以《03》《04》第九章为准。总览级关键约束：

1. 机构绑定审核通过才可见数据；同一"人员+法院+组织"仅一条有效绑定；一人仅一个主驻法院。
2. 智能分案要求带主管标识与普通调解员各至少 1 人；转案池案件不参与智能分案。
3. 关键节点审批不可跳过，全部留痕；驳回类操作（绑定驳回、入驻拒绝、退回案件）原因必填。
4. 提成口径固定为实收−退费；退费累计不得超过实收累计。
5. 期限规则法院×案件类型联合唯一；变更后剩余天数联动重算。

## 十三、AI 赋能与数据能力概要

本章为后续阶段 AI 与数据同步能力的总览级结论，详细设计均已在分册收录，此处不复述。

### 13.1 网页端 AI 智能体（唯一形态：案件内侧边栏）

调解员打开案件详情页，右侧拉出 AI 助手面板，上下文自动绑定当前案件（会话绑定 case_id，切换案件自动切换/清空上下文，不做全局聊天框）；预设快捷按钮（提炼争议焦点/调解话术/协议初稿/风险识别）+ 自由提问，输出支持一键回填调解记录与文书编辑框。

核心原则：**网页只做 UI，AI 计算全部在后端**——前端零密钥，调用经业务后端中转，按任务类型做数据裁剪与脱敏（身份证号/手机号可配置隐藏），长文档由后端摘要压缩后再传模型；每次请求校验登录身份+案件访问权限，调用全程留痕。

能力边界（业务方预期管理）：AI 仅作办案辅助不替代调解员判断；存在幻觉，文书、法条、当事人信息必须人工复核，界面固定提示「**AI生成内容仅供办案参考，正式文书请人工核对修正**」；AI 不处理抓取、截图、定时同步等任务，密钥、账号凭证、Cookie 完全不在前端存放。

交互详设见《04》，后端配置项见《03》系统设置，会话数据表见《05》ai_conversations/ai_messages，接口见《06》AI 智能体模块。

### 13.2 AI 预判盒子（10 个判断点）

工作流 10 个关键判断点封装为**轻量、无状态、可解释、带置信度、人最终拍板**的判断盒子（`POST /api/v1/ai-boxes/{boxKey}/predict`）：受理审查、风险初筛、争议识别、真实性核验、争点归纳、履行能力、策略推荐、协议审查、司法确认推荐、结案方式建议。

原则：**规则优先、LLM 兜底；AI 只给建议不自动执行**结案/终止/司法确认；高敏字段脱敏后进模型；每次调用落 `ai_box_runs` 表（含依据、置信度、人的采纳/推翻、模型版本，留存 ≥5 年），结果渲染在「案件AI分析」标签页与看板预警。MVP 顺序：先规则类，再 LLM 类，最后外部数据依赖类。接口详见《06》五之二。
