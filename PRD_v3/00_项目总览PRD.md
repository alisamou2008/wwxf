## 一、需求背景与价值

### 1.1 项目起源

问问调解（原"问问小法调解平台"）是独立开发的案件调解服务平台，目前已与涪陵区人民法院、万州区人民法院等多家法院建立合作关系，通过飞书多维表进行案件调解工作的流程管理。

随着业务规模的扩大和法院数量的增加，现有飞书多维表工作流在以下方面存在明显不足：

1. **交付体验不佳**：多维表以表格形式呈现，操作复杂，对调解员不够友好
2. **功能受限**：多维表能力有限，无法实现智能分案、AI辅助、动态BI等高级功能
3. **数据孤岛**：各法院数据分散，难以进行全平台的数据分析和监控
4. **权限管理粗糙**：无法实现精细化的角色权限控制
5. **移动端体验差**：调解员在外出调解时操作不便

### 1.2 项目定位与目标（现状基线）

本项目**现状基线**：现有业务（涪陵、万州等法院调解项目）基于飞书多维表运作（调解工作台 84 字段、万州首页等），本平台并非简单照搬，而是**对现有业务逻辑与交互的全面优化重建**——重组流程、重定义口径、重设计交互，在保留业务实质的基础上系统性提升交付效率与体验。

将现有飞书多维表工作流全面升级为独立的网页版SAAS管理后台"问问调解平台"，实现：

1. **全流程重构**：将法院调解全过程的全流程、全环节进行重构，提升调解员操作便利性
2. **管理灵活性**：解决调解平台管理员对所有案件的监控和管理灵活性
3. **数据可视化**：为法院院方提供直观、实时、动态的数据可视化呈现
4. **AI赋能**：通过AI智能体和知识库，帮助调解员提升调解成功率
5. **多法院支持**：天然支持多法院、多调解组织的平台化管理

### 1.3 业务价值

- 对调解员：操作便利、期限可控、文书一键生成，替代多维表手工操作；
- 对调解组织主管：管辖法院数据全景与团队收益透明，管理有据；
- 对平台管理员：全平台监控、智能分案、费用闭环，运营可控；
- 对调解组织：对调解员的工作能力评估可视化，给法院提供严谨的案件整理与分析报告；
- 对法院院方：实时动态的数据可视化，对标分析与监督有抓手。

系统技术选型、数据结构与接口规范不在本 PRD 范围内，详见附件《05_数据库设计文档》《06_API接口设计文档》。

## 二、需求目标

### 2.1 项目范围（分阶段）

**第一阶段（先跑通调解执行业务全流程，含分案与费用）**：

- 用户登录和角色权限系统（两级角色 + 主管标识）
- 机构绑定（法院+调解组织审核，数据可见性总开关）
- 调解驾驶舱（系统管理员首页）+ 数据概览（法院数据对标）
- 调解工作台（调解员首页，含/不含主管标识）+ 法院数据全景（主管标识专属）
- 案件管理系统（列表/详情/多标签页/状态流转，关键节点审批+留痕）
- 待办事项、外呼记录、调解记录、文书管理（含电子签，模板带法院维度，适配不同法官的个性化需求，故模板需要自定义且每个法院可以有多个不同类别的模板）
- 调解进度看板、调解排期日历（操作端专属，调解员/主管）
- 智能分案引擎（三维度权重+人工审核+审计）
- 调解期限规则配置（法院×案件类型，后端规则引擎计算剩余天数）
- 调解费体系（收费规则/费用录入/调解费报表/月结，其中收费规则涉及诉讼费、调解提成、团队激励）
- 基础数据管理（法院/调解组织/人员）
- 系统设置（分案规则/通知/财务/安全）
- 操作日志

**第二阶段（AI 拆案与知识库采用占位）**：

- AI智能体（案件分析/类案检索/调解策略）——**占位**（网页端落地设计已定，见第十六章：案件内侧边栏 AI 助手，与业务表单/案件数据深度联动，后端中转调用）
- 法律法规知识库——**占位**
- AI报表（调解日报/周报/月报自动生成）——**占位**
- 平台首页「每日调解摘要」（依赖 AI）——**占位**
- 案件的AI拆解和分析（随 AI智能体深化调解成功率预测、案件时长预测）
- 类案知识库RAG整理,外部案件整理归类
- 移动端适配（案件信息查询）

## 三、适用角色

### 3.1 两层架构

```
┌─────────────────────────────────────────────────┐
│              问问调解平台                         │
├──────────────────────┬──────────────────────────┤
│      设置层           │       操作层              │
│  （系统管理员）       │  （调解员，可带主管标识）  │
│                      │                          │
│  · 全平台监控         │  · 管辖法院数据查阅       │
│  · 系统设置           │  · 具体案件调解操作       │
│  · 元数据管理         │  · 外呼/文书/AI辅助      │
│  · 智能分案           │  · 个人效能管理           │
│  · 财务审核           │                          │
└──────────────────────┴──────────────────────────┘
```

### 3.2 两级角色 + 主管标识（详见《01》）

登录身份仅两种：系统管理员（admin）/ 调解员（mediator）；「是否为主管」是调解员的管理属性，由系统管理员在注册审核时勾选。带主管标识者拥有调解员全部功能 + ★法院数据全景 + 审批结案 + 全组收益明细查阅。

> 角色定义、权限矩阵、菜单结构等细节以《01_角色与权限设计PRD》为单一事实来源，本文档不复述（避免双处维护漂移）。

### 3.3 业务委派关系（法院 → 调解组织 → 调解员）

```
 法院（业务主体）
   │  委派本院调解案件（一家法院可对接多家调解组织）
   ▼
 调解组织
   │  把法院委派的案件分配给调解员
   ▼
 调解员（带主管标识者兼具管辖职责，既管团队也亲自办案）
```

- 案件链路：**法院**是主体，把案件委派给**调解组织**，组织再分配给**调解员**；案件同时记录所属法院、调解组织、承办调解员。
- 人员通过"机构绑定"获得"法院 + 调解组织"的可见与办理资格，支持一人多法院/多组织（详见《01》《04》）。

关键审批与配置类操作归属：分案全流程、机构绑定审核、主管标识勾选、费用纠错及审核、月结重跑、期限规则/收费规则/系统设置配置、审批结案（主管、调解员都可以作为审批人）、重新指派审核（仅管理员）、主管或调解员对案件的转案申请。详见《01》《03》《04》。

### 4.3 行数据权限（总览级）

- **系统管理员**：全平台全量数据可见可操作；
- **带主管标识的调解员**：管辖法院全量案件 + 本人案件，费用为管辖查阅+本人录入；
- **普通调解员**：仅本人案件与本人费用；
- **数据可见性总开关**：操作层人员须"机构绑定（法院+调解组织）审核通过"才可见对应法院数据，可绑多个法院；绑定停用后（管理员解除绑定）对该法院数据（含历史案件）彻底不可见。

## 五、业务流程

### 5.1 端到端主流程

法院委派案件 → 平台受理（待分案）→ 智能分案（系统管理员：法院选择+三维度权重+人工审核）/转案人工指派 → 调解员承办（调解执行：外呼、调解记录、排期、文书生成与签署）→ 关键节点审批（结案/司法确认/终结，管理员或带主管标识调解员审批+留痕）→ 费用录入（实收/退费逐笔留痕）→ 月结（次月1号生成上月报表快照）→ BI 面板与 AI 报表（后续阶段）呈现。

### 5.2 机构绑定流程

人员注册（选择法院+调解组织，自动生成待审核绑定申请）→ 系统管理员审核 → 通过后可见数据（支持多法院）→ 离职/调岗可停用绑定（彻底不可见）。详见《01》《03》。

### 5.3 调解费与提成模型

```
标的额 ──按收费规则计算──► 应收调解费
                              │ 实际可打折/优惠（人员录入）
                              ▼
                          实收调解费 ──减──► 退费（人员录入）
                              │
                              ▼
                    调解员提成 = 基于实收调解费总和按档位规则核算
```

> **【2026-09-16 口径校准】**：应收调解费口径改为「诉讼费（全国统一标的额分段标准）× 法院比例（40%–50% 逐法院预置）」；提成核算原值改为**实收调解费总和**，具体档位细则待业务补充（见第15章）；旧口径「提成=实收−退费」作为过渡主口径保留在报表快照中。

- **应收**：系统按「诉讼费（全国统一标的额分段标准）× 法院比例」计算（法院比例逐法院配置；旧三模式收费规则保留兼容）；
- **实收、退费**：调解主管/调解员在案件办理中逐笔自行录入并留痕（凭证、方式、折让/退费原因），支持分次收、多次退；
- **提成 = 实收 − 退费**，系统自动计算；**次月 1 号生成上月费用报表快照**，调解员费用做成可下钻到逐案（标的/应收/实收/退费）的数据表，管理端与主管端均展示。

**提成核算细化口径**（源自《调解项目提成核算操作指引-2026版》的阶梯/档位算法，与主口径的采用/融合方式待业务确认）：详见《01》费用模型章节与《03》待确认清单，本文档不复述。

详见《01》第七章、附件《05》费用三表。

## 八、增删改查流转规则

**本章为总览级汇总**，各模块增删改查与状态流转细则详见《03_管理端详细PRD》《04_操作端详细PRD》对应章节。

- **案件状态流转**：待分案→已指派→调解中→待签署→已结案/已结束/已退回；结案/司法确认/终结等关键节点须审批+留痕；申请转案同意后转入转案池并人工指派，不再纳入智能分案。

- **规则配置**：分案/收费/期限规则按法院维度维护，变更不追溯历史案件（应收可单案重算）。

## 九、校验&异常场景

**本章为总览级汇总**，完整校验与异常场景以《03》《04》第九章为准。总览级关键约束：

1. 机构绑定审核通过才可见数据；同一"人员+法院+组织"仅一条有效绑定；一人仅一个主驻法院。
2. 智能分案要求带主管标识与普通调解员各至少 1 人；转案池案件不参与智能分案。
3. 关键节点审批不可跳过，全部留痕；驳回类操作（绑定驳回、入驻拒绝、退回案件）原因必填。
4. 提成口径固定为实收−退费；退费累计不得超过实收累计。
5. 期限规则法院×案件类型联合唯一；变更后剩余天数联动重算。

## 十五、2.0 版本规则校准结论（2026-09-16 会议）

> 本章为 2026-09-16 规则校准会议形成的共识汇总，作为 2.0 版本开发前的一致性基准；具体详设分册同步情况见各文档。按已确认口径：角色模型维持**两级角色 + 主管标识**（详见《01》），会议中“三类核心角色”的权限划分按此模型解读落地。

### 15.1 提成核算规则体系

**核算口径与取值规则**：

1. **唯一核算基准**：提成核算的原值为**实收调解费总和**，彻底规避原规则取值模糊导致的核算逻辑混乱问题。
2. **标的额定位**：案件标的额仅用于前期业务风险判断，**不参与任何提成计算环节**，不纳入提成核算逻辑（标的额仅参与调解费应收计算，见 15.2）。
3. **退费规则**：退费规则的严谨性校验结果、多套优化方案需同步至系统配置，避免调解员自主调整费用影响发放。
4. **系统落地**：所有提成相关规则需形成明确的书面配置文档，确保系统自动核算时无模糊地带，减少人工干预。

**档位与费用标准**：

5. **跨档差异**：单笔费用跨档位导致的提成差额属于**正常绩效差异**，无需针对单案跨档问题做特殊规则调整；此前财务提出的跨档核算差异问题，经重新校验确认无逻辑错误，属正常档位差异，无需调整。
6. **调解费收取标准**：调解费收取标准为对应法院**诉讼费的 40%–50% 区间**，不同合作法院的具体比例已预置在系统应收字段中。
7. **诉讼费取值规则**：诉讼费严格按照**全国统一的标的额对应标准**（分段累计）核算，与案件案由、民事/商业属性无关，无需额外适配；全国统一诉讼费核算标准表需同步至技术团队。
8. **核算逻辑校验**：对现有提成核算 Excel 表的公式逻辑、原值套用规则做全量校验，排查原有规则不严谨导致的核算偏差。

### 15.2 调解费计算公式（各法院规则设定·已确认口径）

```
案件标的额 →〔全国诉讼费分段累计标准（内置于系统）〕→ 诉讼费
诉讼费 ×〔该法院预置比例（40%–50%，逐法院配置）〕→ 应收调解费
实收调解费（逐笔录入）− 退费 → 提成核算原值
```

- 诉讼费按《诉讼费用交纳办法》全国统一标的额分段标准计算，非单一固定比例，与案由/民事商事属性无关；
- 法院比例在「系统设置→各法院规则设定→调解费规则」中逐法院配置（预置于应收字段）；
- 提成规则、调解主管激励规则的档位框架见《03》6.9，具体数值待业务方补充。

### 15.3 角色与权限体系（按两级+主管标识模型解读）

| 会议角色  | 对应系统模型         | 权限定位                                                                     |
| ----- | -------------- | ------------------------------------------------------------------------ |
| 系统管理员 | 系统管理员（设置层）     | 分案管理、法院调解管理、费用审核、转案管理、全量数据操作的最高权限            |
| 调解主管  | 带主管标识的调解员（操作层） | 法院数据看板、调解员案件数据、法院收益明细查阅；核心职责为发现问题、反馈问题（阶段性定位说明：现有 PRD 中主管的结案审批权保留，见《01》） |
| 调解员   | 普通调解员（操作层）     | 本人案件调解、待办事项处理、文书附件记录、个人工作日志，无跨案件操作权限                                     |

- 页面架构：基于现有业务逻辑拆分 30 余个独立功能页面，按角色权限归属做独立配置，避免权限越界。
- **案件返回操作**：调解员无力调解的案件统一走“申请重新指派”流程，由系统管理员统一处理，当前阶段不下放权限；“重新指派”操作与初始分案权限独立拆分；重新指派的案件不纳入智能分案平均分配逻辑，仅做直接换人处理，不回流公共分案池；待重新指派案件量显著提升后再评估下放至调解主管。
- **录音记录字段扩容**：表单字段由 6 条扩容至 15 条，满足调解员日常记录填写需求。
- **调解驾驶舱**：保留数据全景展示，优化案件列表、进度看板可视化效果。
- **文书模板迁移**：飞书多维表内全部标签属性、模板规则完整迁移至新系统，业务逻辑无遗漏。

### 15.4 核心业务流程

**司法确认流程**：司法确认、结案状态无需在自有系统内手动操作，通过代码从官方平台自动同步；仅同步**案件结案状态、结案日期、司法确认申请状态**三类核心字段。

**案件分案流程**：当前分案操作在官方平台手动完成，完成后通过代码同步调解员名下案件数据至自有平台；调解组织账号仅能查看案件基本信息、当事人信息、标的额，无法查看完整证据材料，需适配；流程优化以**最短数据爬取路径**为核心目标；单台服务器运行所有同步代码，需合理编排运行顺序（当前：案件爬取代码全天循环运行，司法确认等状态同步代码每日下班前运行一次）。

**案件逾期处理**：默认办理时效**简易程序 7 天、普通程序 15 天**，超期需提前走延期申请；延期仅可申请 **1 次，固定延长 30 天**，需双方当事人签署延期申请书后上传官方平台完成；案件到期前 2–3 天，由对应调解员提前联系当事人确认调解意向，确认可继续调解的再走延期流程。

### 15.5 技术选型与存储方案

**电子签供应商**：选型优先级为①身份校验严谨性→②模板配置灵活性→③服务性价比；已对接腾讯电子签（千份套餐模式）与重庆本地服务商（预充值模式），单份约 0.6 元，日均 1–2 单，待比对后确定测试供应商；供应商需支持直接上传 Word 模板完成配置；官方平台可覆盖的签署场景优先使用官方免费服务，仅延期等官方未覆盖场景使用第三方电子签。

**数据存储**：当前阶段优先采用**飞书多维表**作为数据存储介质，仅保留数据存储、查看功能，关闭所有前端操作权限（运维成本极低、字段调整可直接操作）；多维表仅作为数据流转的中间存储介质，不开放为前端操作入口；针对误编辑/误删风险通过权限锁死、定期备份规避；已知附件存储格式限制问题当前不调整，后续评估；待业务量增长后再评估切换独立云服务器数据库。

**分案系统对接**：当前仅同步调解员账号下案件数据；所有对接逻辑适配官方平台现有规则，不强行修改官方平台固有操作逻辑；数据同步优先采用自动化代码，减少人工介入。

## 十六、网页端调解AI智能体方案（AI 赋能·网页端落地设计）

> 本章为在网页端为调解员内置 AI 智能体的方案基线（2026-09-17 补充），业务场景：案情摘要提炼、调解话术生成、风险提示、调解文书初稿、案件标签识别、咨询调解员工作量建议等，**与业务表单、案件数据深度联动，不是独立聊天窗口**。属第二阶段 AI 赋能范围，与既有「AI智能体（占位）」条目合并实施。

### 16.1 核心原则：网页只做 UI，AI 计算全部在后端

```
调解员Web网页端（仅聊天/表单界面，不存任何密钥）
    ↓（携带登录token、案件ID）
调解平台后端
    ├─权限校验：确认该调解员有权访问这个案件
    ├─读取数据库：提取本案件需要的业务数据（案情、调解记录）
    ├─数据裁剪/脱敏：只提交本次AI任务所需字段，敏感字段可配置隐藏
    ├─构造Prompt（系统提示词+案件业务上下文+用户提问）
    ├─调用大模型API（DeepSeek/豆包等，密钥仅存后端）
    └─返回AI结果给网页渲染
        ↓
网页：展示AI回答，支持一键回填到调解表单
```

- **绝对禁止**：浏览器 JS 直接写 API-KEY 调用大模型——密钥会暴露在网络请求、开发者工具中，会被盗刷额度。前端永远接触不到 API 密钥，AI 调用必须经业务后端中转。

### 16.2 主要现实障碍与应对

| #   | 障碍         | 应对口径                                                                            |
| --- | ---------- | ------------------------------------------------------------------------------- |
| 1   | 前端不能存放模型密钥 | 所有调用走后端代理（见16.1架构）                                                              |
| 2   | 业务上下文传递    | 后端按 AI 任务类型做**数据裁剪**，只传本次任务所需字段，不无脑全量丢案件原文；当事人隐私数据属敏感个人信息，需脱敏配置（身份证号/手机号可配置隐藏）  |
| 3   | 会话记忆绑定     | AI 会话**绑定具体案件 ID**，数据库存会话历史（每条关联案件+操作人）；切换案件自动切换/清空上下文，避免不同案件案情串扰；不做全局聊天框       |
| 4   | 浏览器能力边界    | 网页端只做对话展示、表单辅助填充、生成文本回填；抓取/截图识图/定时任务保留后端 Python；本地不跑模型，走云端 API；长文档由后端做摘要压缩后再传模型 |
| 5   | 业务预期       | AI 存在幻觉（当事人名字写错、法条引用错误），界面固定醒目提示：**「AI生成内容仅供办案参考，正式文书请人工核对修正」**                 |
| 6   | 权限隔离       | 每次 AI 请求后端校验登录身份+案件访问权限，调解员 A 不能经 AI 接口查询调解员 B 的案件资料                            |

### 16.3 网页端形态：只做案件内侧边栏

**案件详情页侧边栏 AI 助手（本方案唯一形态）**：打开具体案件详情页，右侧拉出 AI 助手面板，上下文自动绑定当前案件。调解员可提问（如“帮我写一段调解沟通话术”“总结本案争议焦点”“生成调解协议书草稿”），AI 读取当前案件数据输出，支持一键复制/直接回填页面表单。详见《04》案件详情页设计。

不做独立全局 AI 聊天页面（不绑定案件、手动粘贴案情，不适合调解员高频办案；管理员查询分析需求后续再评估）。

### 16.4 交互与功能设计要点

1. **预设快捷按钮 + 自由提问**：调解员操作高度重复，页面放置快捷按钮——提炼案件争议焦点 / 生成调解沟通话术 / 生成调解协议初稿 / 案件风险识别（可扩展案情摘要、案件标签识别、工作量建议）；点击按钮即带当前案件 ID 调后端固定指令，降低输入成本。
2. **回填能力**：AI 输出文本支持一键回填到调解记录、文书编辑框，调解员在此基础上修改，不做纯复制粘贴。
3. **限流控制**：后端增加调用频率限制，防止高频调用消耗大量 AI 额度。
4. **调用日志**：每次 AI 调用记录操作人、案件 ID、输入、输出，可追溯。

### 16.5 能力边界（写入业务方预期管理）

1. AI 智能体仅作**办案辅助工具，不替代调解员判断**；
2. AI 存在幻觉，文书、法条、当事人信息**必须人工复核**；
3. AI 智能体**不处理**抓取、截图、定时同步等任务，数据来源依旧是后端 Python 抓取链路；密钥、账号凭证、Cookie 完全不在前端存放。

分册同步：交互详设见《04》案件详情页，后端配置项见《03》系统设置 AI 模型配置，数据表见《05》ai_conversations/ai_messages，接口见《06》AI 智能体模块。

## 十七、调解员工作流基线与 AI 预判盒子（2026-09-20 同步）

> 来源：《调解员工作流-完整版》《调解工作流-AI预判盒子技术方案》《调解案件全字段清单 v1》三份基线文档。

### 17.1 调解员工作流 8 阶段（案件生命周期）

0. **案件进入与受理审查**：管辖、可调解性、排除情形（人身关系禁止调、无/限制行为能力、涉刑、已诉不宜委派、损害公益/第三人）、材料完整性、关联案件/涉众/保全；不受理→退回/转立案留痕
1. **案情掌握与初步研判**：阅卷、身份与代理权限核验（特别授权才能代签）、回避审查、可调性/风险（虚假调解、信访、涉众）/策略初判
2. **通知与意愿确认**：送达《受理告知书》《权利义务告知书》，取得**在线调解明示同意**（`consentRecordId`，电子签前置），确认调解意愿
3. **争议识别与分类**（关键分叉）：调解意愿与有无争议是**两个独立维度**；无争议→4A，有争议→4B
4A. **无争议处理**：真实性核验（防虚假调解/恶意串通/损害第三人/胁迫）→ 记载无争议事实 → 拟方案 → 履行能力评估
4B. **有争议处理**：争点整理 → 举证指导/证据交换/质证、固定无争议事实 → 法律释明与裁判预判 → 背对背/面对面策略 → 多轮方案比选 → 必要时引入第三方 → 履行能力审查
5. **协议形成与签署**：协议内容审查（合法/可执行/自愿）→ 制作《调解协议书》→ 电子签署三阶段（当事人→调解员→组织盖章）→ 送达回证 + 存证
6. **效力固化**：司法确认（生效后 30 日内共同申请，到期前 7 天提醒）/ 赋强公证 / 撤诉；即时履行完毕→结案
7. **结案与归档**：结案方式分类（成功-司法确认/撤诉/即时履行；不成-终止；撤回；转立案）、卷宗归档、结案审批留痕、数据回流
8. **回访与履行跟踪**：履行回访、满意度、不履行预警→提示司法确认/执行

横切支撑：期限管理（诉前 30 日、临期预警 <10 橙/<5 红、超期必须结案/转立案）、流程留痕审计、数据分级脱敏（L3/L4）、中止/终止/移送分支。

### 17.2 案件状态机（v3 新增基线）

`待分案（管理端指派）→ 已指派（调解员接收，无受理确认）→ 研判中 → 通知中(待明示同意) → 意愿确认(愿/不愿) → 争议识别(无争议/有争议) → 调解中(协商/举证/方案) → 待签协议 → 签署中 → 待效力固化(司法确认/赋强/撤诉) → 已结案(成功/不成/撤回/转立案)`

看板列、待办/临期规则均对齐该状态机。详见《04》业务流程章节。

### 17.3 AI 预判盒子（"判断盒子"理念）

把工作流 10 个关键判断点封装为**轻量、无状态、可解释、带置信度、人最终拍板**的判断盒子（`POST /api/v1/ai-boxes/{boxKey}/predict`）：`admissibility`（受理审查）、`risk_screen`（风险初筛）、`dispute_detect`（争议识别）、`authenticity`（真实性核验）、`issue_extract`（争点归纳）、`enforceability`（履行能力）、`strategy_advice`（策略推荐）、`agreement_review`（协议审查）、`confirm_advice`（司法确认推荐）、`closure_advice`（结案方式建议）。

原则：规则优先、LLM 兜底；AI 只给建议不自动执行结案/终止/司法确认；高敏字段脱敏后进模型；每次调用落 `ai_box_runs` 表（含依据、置信度、人的确认/推翻、模型版本，留存 ≥5 年）。结果渲染在「案件AI分析」标签页与看板预警。MVP 顺序：先规则类（admissibility/confirm_advice/期限临期），再 LLM 类，最后外部数据依赖类。详见《06》AI 判断盒子接口。

### 17.4 案件全字段基线（91 字段）

《调解案件全字段清单 v1》（源：人民调解平台截图 + 工作流新增字段 + 原飞书表）共 91 个字段，覆盖：基本信息 19、当事人 15、流程状态 4、阶段0 受理审查 6、阶段1 研判 8、阶段2 通知与意愿 5、阶段3 争议识别 3、阶段4 处理 8、阶段5 协议签署 4、阶段6 效力固化 3、阶段7 结案归档 2、阶段8 回访履行 4、期限管理 2（期限预警为公式字段：正常/临期5日内/已超期）、附件与动态 8。字段级清单与数据表映射见《05》《04》。

分册同步：8 阶段工作流与状态机 → 《04》业务流程；91 字段与 `ai_box_runs` 表 → 《05》；`/ai-boxes/*` 接口 → 《06》。

## 十八、核心功能模块框架与技术分层架构（2026-09-20 同步）

> 来源：《调解平台-核心功能模块框架》《调解平台-技术分层架构》两份基线文档。平台顶层能力结构为「**3 业务模块 + 横切 AI 赋能层 + 共享底座**」，技术上对应**五层架构**。

### 18.1 核心功能模块框架（3 业务模块 + 横切 AI 层 + 共享底座）

```
        ┌──────────────────────────────────────────────────┐
        │  AI 赋能层（横向 · 辅助，非第 4 业务模块）              │
        │  预判盒子 · 分案算法 · 费用稽核 — 嵌入前三模块，人拍板   │
        └───────────┬──────────────┬──────────────┬─────────┘
        ┌───────────▼──┐  ┌────────▼─────┐  ┌───────▼─────┐
        │ ① 智能分案    │→ │ ② 调解执行    │→ │ ③ 费用处理   │
        │  治理/管理层  │  │  操作层       │  │ 管理+操作    │
        └──────┬───────┘  └──────┬─────┘  └──────┬─────┘
        ┌──────┴─────────────────┴───────────────┴─────────┐
        │  共享底座 / 平台中台（三模块共用）                    │
        │  电子签中台 · 实名认证 · 期限引擎 · 消息送达 · 卷宗审计 · 权限 │
        └─────────────────────────────────────────┘
```

**三个业务模块**：

| 模块 | 层级 | 回答的问题 | 平台落点 |
|------|------|-----------|---------|
| **① 智能分案** | 管理/治理层（仅系统管理员，主管与调解员不碰） | 案子怎么分到对的调解员 | 智能分案：法院选择 + 三维度权重 + 人工审核 + 分案记录（`assignments`/`assignment_audit_logs`） |
| **② 调解执行** | 操作层（调解员/主管） | 案子怎么调成 | 完整工作流 8 阶段（见第十七章）：受理审查 → 通知+明示同意 → 争议识别分叉 → 调解/沟通 → 协议签署（电子签三阶段）→ 效力固化 → 结案归档 → 回访 |
| **③ 费用处理** | 管理+操作（费用月结在管理端，提成在双端） | 钱怎么算、怎么结 | 调解费报表/收费规则（应收·实收·退费）；调解员提成核算。人民调解本身不收费，"费用"含两层——当事人侧（司法确认费/公证费/诉讼费减免）+ 调解员侧（提成） |

**已锁定的两点边界**：
1. **智能分案 = 仅管理端操作**：法院×权重 + 人工审核 + 分案记录，**不含**承办人匹配/排期冲突（后者归属模块②的「排期日历」）。
2. **AI 是横切赋能层，不是排第 4 的业务模块**：从第一天就嵌在分案（推荐算法）、执行（预判盒子）、费用（异常稽核）里，不拥有独立数据闭环，结果回流到对应业务页面（如「案件AI分析」标签页、看板预警）；原则沿用第十七章 17.3（规则优先、人拍板、留痕可审计）。
3. **共享底座单独成层**：电子签、实名认证、期限引擎、消息送达、卷宗审计、权限/回避既不是"执行"也不是"AI"，但三模块都依赖，显式独立，避免 PRD 重复建设。

### 18.2 共享底座能力清单

| 底座能力 | 说明 | 跨模块作用 |
|----------|------|-----------|
| 电子签中台 | 腾讯电子签渠道版 + 防腐层 | 调解协议/司法确认/送达回证/费用收据 |
| 实名/人脸核身 | L4 高敏，生物特征不落库 | 分案主体核验、签署前置 |
| 期限规则引擎 | 诉前 30 日、按法院×类型可配、临期预警 | 执行（看板剩余天数）、司法确认 30 日倒计时 |
| 消息/送达 | 短信/微信/站内/邮寄/公告 | 通知当事人、催签、送达回证 |
| 卷宗/审计 | 全量操作日志 ≥5 年、卷宗保管 | 三模块通用合规留痕 |
| 权限/回避 | RBAC（管理员/主管/调解员/当事人/法院） | 三模块通用访问控制与回避校验 |

### 18.3 技术分层架构（五层）

```
┌─────────────────────────────────────────────────────────────┐
│ L1 前端层    AdminLayout(管理端) · MediatorLayout(操作端) · H5签署页 │
└───────────────────────────────┬─────────────────────────────┘
                                 │  HTTPS /api/v1 (统一网关)
┌───────────────────────────────▼─────────────────────────────┐
│ L2 业务服务层  统一API网关(BFF) · 智能分案域 · 调解执行域 · 费用域      │
│             （案件/当事人/调解记录/外呼/看板/排期/BI）                │
└──────┬───────────────────────────────────────┬─────────────┘
       │ 内部调用 /ai-boxes/*                    │ 内部调用 /sign-flows/*
┌──────▼──────────────────┐          ┌──────────▼──────────────┐
│ L3 AI 中台              │          │ L4 签署中台                 │
│  预判盒子编排·规则引擎    │          │  签署防腐层·状态机·存证·司法确认  │
│  LLM网关·法规RAG·样本库   │          │  EssGateway → 腾讯电子签 essbasic │
└──────┬──────────────────┘          └──────────┬──────────────┘
┌──────▼───────────────────────────────▼───────────────────────┐
│ L5 共享底座   实名/人脸核身 · 期限规则引擎 · 消息送达 · 卷宗审计 · RBAC · 文件存储 │
└─────────────────────────────────────────────────────────────┘
```

- **L1 前端**：Vue3 + Vite + Element Plus + Pinia（ECharts、fullcalendar、vuedraggable）；仅调 `/api/v1/*`，不接触模型密钥与腾讯 AK/SK；H5 签署页不进主框架权限。
- **L2 业务服务层**：Supabase（PostgreSQL + RLS）+ Edge Functions/自建服务，BFF 网关做路由、鉴权、限流、幂等、审计埋点；按 3 业务模块划分分案/执行/费用三域；**不含任何厂商/模型直连**。
- **L3 AI 中台**：10 个预判盒子（见 17.3），规则引擎 + LLM 网关 + 法规 RAG + 脱敏网关；只出建议不自动改状态。
- **L4 签署中台**：签署防腐层·状态机·存证·司法确认，EssGateway 翻译腾讯字段；服务端强校验合规红线（人身关系黑名单、在线调解明示同意、阶段顺序、核身/印章/代签限制）。
- **L5 共享底座**：即 18.2 清单，以 SDK/中间件形式被三层调用，不独立对浏览器暴露。

**防腐层是架构红线**：L2 业务代码里不得出现 `FlowId`/`Approver` 等腾讯概念，也不得出现模型厂商 endpoint；换签厂商/换模型只改对应中台，业务层零改动。鉴权、脱敏、审计（≥5 年）、幂等横切 L2/L3/L4；接口逻辑归属映射见《06》五之三。

### 18.4 五层 ↔ 业务模块映射与演进

| 业务模块 | 主要承载层 |
|---|---|
| ① 智能分案 | L2 分案域 + L5 权限/审计（推荐算法若入 L3 后置，本期规则+人工） |
| ② 调解执行 | L2 执行域（主）+ L4（签署/司法确认）+ L3（预判盒子）+ L5（核身/期限/消息/审计） |
| ③ 费用处理 | L2 费用域 + L5 审计 |
| 横切 AI 赋能 | L3 AI 中台（不独立成业务模块） |

**演进顺序**：① 先立 L5（鉴权/审计/RBAC/期限引擎）+ L2 业务骨架 + L1 三端，跑通无 AI、无电子签的纯线下调解闭环（文书可上传扫描件）；② 再接 L4 签署中台（腾讯企业自动签白名单为最长等待项）；③ 后上 L3 AI 中台 MVP（3 个规则盒子）。下一阶段产物：各层服务契约 OpenAPI（需补 L2 业务域）、数据库 schema/RLS、网关路由与鉴权中间件设计。待确认：智能分案算法是否本期纳入 L3（建议后置）。
